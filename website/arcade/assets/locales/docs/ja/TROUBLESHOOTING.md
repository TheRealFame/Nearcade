### 1. 視聴者には黒い画面が表示されます

**症状:** ビューアは正常に接続します (名簿が表示され、音声も機能する場合もあります) が、ビデオが常に真っ黒になります。

**この問題が発生する理由:** WebCodecs デコーダにはコーデック構成が与えられていません。これは既知の競合です。ホスト ネットワークがバックアップするとき、ホストはストリームを維持するために重要でないデータを意図的にドロップしますが、ビューアの `VideoDecoder` を起動する JSON 構成パケットを**決して**ドロップしてはなりません。そのパケットが失われた場合、デコーダは初期化できず、ネットワークが回復した後でも永久に黒のままになります。

**修理：**
1. ビューアにページを更新してもらいます (F5)。ただ待つだけではありません。
2. それでも繰り返し発生する場合は、ホストのビットレート/解像度を 1 段階下げて再接続します。ストレスが少ない = 強制落下が少なくなります。
3. インターネット アップロードが飽和していないことをホストに確認します (緑色の「ライブ」錠剤は問題ありません。黄色/赤色の錠剤はエンコーダがバックアップ中であることを意味します)。

### 2. ストリームの遅延は時間の経過とともに徐々に悪化します

**症状:** ゲームは最初は正常に動作しますが、10 ～ 20 分後にはライブ ビューがどんどん遅れていき、自然に回復することはありません。

**この問題が発生する理由:** WebRTC データ チャネルと WebSocket は **無限に**バッファします。ドロップを強制するものがない場合、エンコーダは古いフレームをゆっくりとキューに入れ、遅延が永続的になります。 Nearcade は、古いフレームを削除し、キーフレームを強制する `bufferedAmount` チェックを使用してこれを強制します。ただし、古いセッション (または現在のビルドより前に開始されたセッション) が実行されている場合、その保護は適用されない可能性があります。

**修理：**
1. まず、セッションを停止して再起動します (古いバッファを削除します)。
2. サイズが増大し続ける場合は、ホスト クライアントを最新のビルドに更新します。
3. 負荷の高いダウンロードと同じ接続を共有している Wi-Fi 上でホストを実行しないようにします。

### 3. VIP セッションがコントロールに接続しない (接続中のままになる)

**症状:** ビデオは動作しますが、ボタンやコントローラーが反応しません。または、セッション全体が 15 秒以上「接続中…」のままになります。

**その理由:** WebRTC には STUN/TURN 候補が必要です。ネットワークが型指定されたプロファイル間で切り替わる場合 (例: デッドまたは低速のパブリック TURN リレーがプール内にある場合)、特定のサーバーがタイムアウトになるまでハンドシェイクが数秒間停止する可能性があります。このはしごでは、まず高速で信頼性の高いサーバーを試し、次に最後の手段としてコミュニティ リレーを試すことになっています。

**修理：**
1. 最大 25 秒ほど待ちます。最終的にはしごがフェイルオーバーして接続します。
2. 数分間ハードな「接続中」画面が表示される場合は、ビューア URL をハード更新します (または、末尾に `/` を付けずにリンクを再度開きます)。
3. ホストの場合: [設定] → [コミュニティ TURN サーバー] で独自の信頼できる TURN サーバーを追加します。応答性の高いカスタム リレーにより、ハンドシェイクがほぼ瞬時に行われます。

### 4. ゲームによって作成されたことのない仮想コントローラー

**症状:** ビューアはゲームパッド モードとして参加しましたが、ゲームにコントローラーが表示されません。

**この問題が発生する理由:** 仮想コントローラーはカーネル側ドライバーによって作成されます。このドライバーには、Linux ではインストール時に付与されたプライベート ドライバー、または Windows ではサードパーティの ViGEmBus ドライバーが必要です。

**修理：**
- **Windows:** ViGEmBus をインストールします (セットアップ ウィザードでこのためのプロンプトが表示されます)。ドライバーが [デバイス マネージャー] → [ソフトウェア デバイス] → [*ViGEm Bus Enumerator*] の下に存在することを確認します。
- **Linux:** ホストには `/dev/uinput` への書き込みアクセスが必要です。セットアップ スクリプトを確認します。`bin/linux_setup.sh` (または `sudo modprobe uinput`) を実行し、ホストを再起動します。
- wingamepad が *以前は動作していた*がその後停止した場合は、ホスト アプリが運転中に更新されていないことを確認してください。入力ハンドラーは Web UI と同じバージョンで実行されている必要があります。ホスト アプリを完全に再起動します。

### 5. ホストがシャットダウンした後の耳をつんざくような音声ノイズ (Linux)

**症状:** ホストが終了すると、スピーカーから大きな継続的なブザー音が鳴り止みません。

**この問題が発生する理由:** Linux 仮想オーディオ エンジンは特定の順序で破棄されます。ループバック モジュールはヌルシンクの前**にアンロードされる必要があります。順序を逆にすると、ループバック ワイヤがデッド シンクを指したままになり、PulseAudio が強制終了されるまでバズ音が発生します。

**修正 (即時):**
```bash
pactl list short modules   # note the module IDs
pactl unload-module <loopback_module_id>   # unload ringback FIRST
pactl unload-module <null_sink_module_id>  # then the sink
```
停止しない場合は、オーディオ デーモンを再起動します。
- パルスオーディオ: `pulseaudio -k && systemctl --user restart pulseaudio`
- パイプワイヤー: `systemctl --user restart pipewire pipewire-pulse`

セッション中にアプリを強制終了するのではなく、ホスト UI から通常の「セッションの停止 / 終了」ボタンを常に使用してください。アプリはクリーンな終了時に正しい順序でこのティアダウンを実行します。

### 6. 音声チャットのエコーまたはフィードバック

**症状:** 視聴者は自分自身の声を聞くか、ホストのデスクトップが再生するすべての音声を聞きます。

**その理由:** 視聴者の音声はホストの物理出力デバイスにルーティングされます。代わりに *仮想* キャプチャ シンクにルーティングされると、ゲーム オーディオ ループバックがそれらを拾い上げ、無限のエコーを作成します。

**修理：**
1. ホスト: ルーティングは自動です。「アプリケーション オーディオ」キャプチャが専用の仮想シンク (デスクトップ/ヘッドフォン シンクではない) を使用していることを確認します。
2. ホストのオーディオ出力デバイスを変更した後にエコーが発生した場合、ホストはデバイス設定に戻り、ボイスチャット用に物理出力 (仮想シンクではなく) を選択する必要があります。

### 7. 非常に弱いネットワーク上でホスト/キャプチャが失敗するか、視聴者がデバイスを駆動するとセッションが切断される

**症状:** 多くの視聴者が参加/退出するとき、または誰かが重い処理 (ストリーミングと VR を同時に実行するなど) を有効にすると、キャプチャが停止したり、名簿がフリーズしたり、ホストが切断されたりします。

**この問題が発生する理由:** 積極的なフレーム ドロップとホットスワップ ティアダウンはリソースを大量に消費します。弱いホストではこれが飽和し、ブラウザは飛行中にストリームを再利用します。

**修理：**
1. ホストの最大解像度/ビットレートを下げます。
2. **外部** (Discord/OBS) にブロードキャストする場合は、「入力のみ」モードを使用します。これにより、外部キャプチャのためのビデオ処理が停止し、マシンが解放されます。
3. 「ホスト遅延等化」を有効/オンのままにします。エンコード/送信時間を動的に考慮するため、ジッターが発生しても入力の同期が維持されます。
4. VR の場合: WiVRn RGB と仮想サウンドをセッションと同じネットワーク セグメント外に保ちます。

### 8. 名簿にゴースト/重複プレイヤーが表示される

**症状:** プレーヤーが退出した後も名簿に残っているか、2 回出場しています。

**理由:** Roster DOM は非同期 WebSocket メッセージから再レンダリングされます。古典的なバグは、別のティックで古い要素の後に新しい要素を追加し、重複を生成することです。修正されたコードは同じ同期ブロック内でクリアおよび再構築されます。これがまだ表示される場合は、クライアントが古いことになります。

**修理：**
1. ホスト (`Ctrl+Shift+R`) をハードリフレッシュします。
2. ソースからカスタム ホスト クライアントを実行する場合は、最新のビルドをプルします。
3. 数秒待ちます。サーバーは死んだ視聴者を独自に削除します。

### 9. 視聴者は離れましたが、コントローラーは「押された」ままです

**症状:** 誰かが退席した後、ゲーム内でキー/ボタンが押されたままになります。

**理由:** ホストは、切断時に押したボタンが解放されるように、「休止状態」ペイロードを再生する必要があります。これは、切断が適切に処理された場合 (視聴者が [終了] をクリックした場合) に機能します。ビューアのタブが突然強制終了された場合、仮想コントローラはサーバーのハートビートが期限切れになるまで存続する可能性があります。

**修理：**
1. 古いビューアを名簿からキックします (キック パスにより強制的にリリースされます)。
2. スロットが差し戻されてスタックした場合は、ビューアのスロット ロックをオフからオンに切り替えるか、セッションを再起動します。仮想デバイスは破棄され、完全に再作成されます。

### 10. ハードウェア変更後の永続的な「未処理例外」画面

**シナリオ:** セッションが E99 で終了し (または赤いエラー トーストが表示されます)、セッションを再起動しても問題が解決しません。 GPU またはオーディオ デバイスを追加または削除した後。

**理由:** アプリは無効な MediaStream/`peerConnection` への参照を保持しており、変異に最も近い `try/catch` が欠落しているため、クリーンアップの前にティアダウンがスローされます。

**修理：**
1. ホスト アプリを完全に終了します (セッションを閉じるだけではありません)。
2. OS レベルのオーディオ/GPU ドライバーが正常であることを確認します (デバイスは他のアプリから引き続き認識されます)。
3. ホストを再度開きます。クリーンアップ フックは、各トラックの try/catch およびハードストップ/null でティアダウンをラップするようになりました。これにより、古いデバイス ハンドルが解放されます。
4. ゲームがストリームに貢献していない場合は、インスタンスを削除して再度追加します。

## 自分で簡単にデバッグする

- **ホスト** ページ → [コンソール] タブでブラウザ DevTools (`Ctrl+Shift+I`) を開きます。 `[WebRTC]` メモ (ラダー テレメトリ)、`[PPS]` (ビューアー フラッド キック)、`[Congestion]` (ビットレートの理由)、および `[codec]` (H264/VP9 の選択と iGPU 検出) を探します。
- `npm test` (ソース ビルドのみ) サーバーを検証します: ブート、仮想オーディオ、REST API、WebSocket ハンドシェイク — `Verification Complete!` はコアが正常であることを意味します。
